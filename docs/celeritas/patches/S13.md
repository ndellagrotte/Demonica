# S13: the fast block renderer under a shader pack, and its switch

Draft, not sent. Replaces `seam.VintageBlockRendererMixin` and the switch in
`seam.ChunkBuilderMeshingTaskMixin` (group MESHING).

## Problem

**The switch.** `ChunkBuilderMeshingTask.USE_NEW_BLOCK_RENDERER` is true in a
deobfuscated environment and otherwise only with
`-Dceleritas.useVintageFastBlockRenderer` (`ChunkBuilderMeshingTask.java:44`), so a
dev client and a player's client mesh blocks differently. Demonica reads the switch
from its own option, `performance.use_fast_block_renderer`, the same in both, and
off by default like upstream's production setting. The switch is per block: some
mods render or hide blocks from inside vanilla's `BlockRendererDispatcher`, which
the fast renderer bypasses, so those blocks always take the vanilla path
(`FastBlockRendererCompat`): Snow! Real Magic!'s snow layers (it re-emits the
covered block from inside `renderBlock`), ArchitectureCraft's blocks (its own
dispatcher draws them; their baked models are missing), and, with the Component
Model Hider, every block next to a hidden one (the hider's redirects in
`BlockModelRenderer` stop a hidden block from culling its neighbours' faces).
Actinium also skipped missing models on the fast path, because Forge's
`FancyMissingModel` draws its label with a font renderer; Demonica kept that
renderer off its GL font batcher instead (commit a4dc4263), and has no font
batcher since 0.3.0, so missing models render as in vanilla on both paths.

**The fast renderer under a pack.** `VintageBlockRenderer` does not do what the
modern loaders' `BlockRenderer` does for Iris:
- It writes quads without a block context (`BlockRenderer` calls
  `ContextAwareChunkVertexEncoder.prepareToRenderBlockFace`).
- It always writes colours with `ChunkColorWriter.EMBEDDIUM`
  (`VintageBlockRenderer.java:215`); `BlockRenderer` picks `SEPARATE_AO` when the
  pack asks for ambient occlusion in the alpha channel (`BlockRenderer.java:110`).
- It applies directional shading even when the pack turns it off
  (`oldLighting=false`; the modern `FluidRenderer` checks it at `:413`).
- It meshes fluid blocks like any other: the sprite analysis can change their
  material, and translucent ones go to the translucent pass instead of the pack's
  water pass (S14).
- The render-pass optimisation can move a block the pack put in a layer (S10) back
  out of it.

## Proposal

- Make the switch an option (`CeleritasVintage.options()`), with one default for
  dev and production, and consult a list of blocks that must stay on vanilla's
  dispatcher (mods could register predicates; the three above would be the first).
- In `VintageBlockRenderer`: per block, the provider's block context, prepared on
  the encoder of each builder the block writes to and finished at the end
  (as `BlockRenderer` does); the colour writer and the `shade` flag from the
  provider's lighting settings; for fluid blocks, the provider's fluid material and
  no sprite analysis; no render-pass optimisation for a block whose layer the
  provider overrides.

## What Demonica drops

`VintageBlockRendererMixin` (8 injectors: the block context at HEAD and RETURN of
`renderBlock`, the encoder around `writeGeometry`, the fluid material twice, the
render-pass flags, the `shade` flag, the colour writer) and the
`@ModifyExpressionValue` on the `USE_NEW_BLOCK_RENDERER` read (which takes the
block and its position from the loop's locals).

## Not the same as the vanilla path

The vanilla path draws through vanilla's `BlockModelRenderer`, which bakes its own
directional shading and ambient occlusion into the vertex colours. Packs that turn
directional shading off or want separate ambient occlusion (BSL and Complementary
do both) therefore shade blocks differently depending on the path. Actinium behaved
the same way; matching them needs hooks in vanilla's renderer during meshing.
