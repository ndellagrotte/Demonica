# O1: getters on the option controls

Draft, not sent. Replaces `internal.SliderControlMixin` and `internal.CyclingControlMixin` (group OPTIONS).

## Problem

Demonica's video settings screen is Reese's Sodium Options (RSO), which draws
Celeritas's options (`org.taumc.celeritas.api.options`) with its own row widgets
instead of the controls' `createElement`. For that it needs what the controls were
built with, and two of them keep it private:
- `SliderControl`: `min`, `max`, `interval` and the value formatter (`mode`), to
  draw the slider, step it, and label the value;
- `CyclingControl`: `allowedValues`, to step through the values and label the
  current one (`getNames()` is public; the values are not).

Actinium's fork added the getters. Every other control RSO draws (`TickBoxControl`)
needs nothing beyond the public API.

## Proposal

```java
// SliderControl
public int getMin() { return this.min; }
public int getMax() { return this.max; }
public int getInterval() { return this.interval; }
public ControlValueFormatter getFormatter() { return this.mode; }

// CyclingControl
public T[] getAllowedValues() { return this.allowedValues.clone(); }
```

Read-only, no behaviour change.

## What Demonica drops

Both mixins, the ducks `SliderControlAccess` and `CyclingControlAccess`, and the
availability check in `OptionControls` (`com.demonica.celeritas.options`), which
reads the getters instead. Without the patch, RSO cannot draw sliders or cycling
options, so Video Settings keeps Celeritas's own screen (`OptionsScreens`), which
also lists Demonica's settings.

## Not needed from upstream

The rest of Actinium's option-API extensions have no upstream counterpart to ask
for:
- the applied value and undo: `Option.hasChanged()` already compares the pending
  value with the applied one, and `Option.reset()` is undo;
- declared defaults for the reset button: the pages that know their defaults
  declare them to RSO (`OptionDefaults`);
- group names: no page ever set one;
- `ExternalPage` and `ExternalButtonControl`: they live in RSO;
- page contributions: Demonica's settings join Celeritas's pages through
  `OptionGroupConstructionEvent`, `OptionPageConstructionEvent` and
  `OptionGUIConstructionEvent`, as their documentation intends.

One small upstream change would still help both screens: `EventHandlerRegistrar.post`
runs the listeners in one loop, so a listener that throws ends it. In Celeritas's
screen the exception escapes the screen's constructor; RSO catches it
(`OptionGUIConstructionBridge`), but the listeners after the broken one add no
pages. Catching and logging per listener in `post` would fix both.
