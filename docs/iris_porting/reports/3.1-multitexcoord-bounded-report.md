## What changed

Paths under `shader/src/main/java/net/coderbot/iris/pipeline/transform/transformer/`.

- `CommonTransformer.java`: new public `replaceGlMultiTexCoordBounded(ShaderAst ast, int minimum, int maximum)`: a loop
  of `ast.replaceExpression("gl_MultiTexCoord" + i, "vec4(0.0, 0.0, 0.0, 1.0)")`. It is the DH transformers' private loop
  lifted, not Iris's idiom code (`root.replaceReferenceExpressions` over a prefix query). The `// Demonica:` comment says
  why: every caller runs it among other ShaderAst verbs (PORTING_GUIDE rule 3), it keeps the DH output byte-identical,
  and it replaces only reference expressions, as Iris does. It also matches exact names, so it never reaches Iris's
  `Integer.parseInt` of the suffix.
- `AttributeTransformer.java`: 4-7 after `patchMultiTexCoord3` (upstream order, with upstream's comment).
- `CeleritasTransformer.java`: 4-7 after the `vertexReplacements` (0-2). Upstream runs it after `patchMultiTexCoord3`,
  which D runs later in `ShaderTransformer.doTransform`. The `// Demonica:` comment notes that the names do not overlap.
- `CoreTransformHelper.java` (`injectCompositeVertexAttributes`): 1-7 before the `gl_MultiTexCoord0` rename. Upstream
  replaces 0 with `vec4(UV0, 0.0, 1.0)` first and then 1-7. D keeps its `iris_MultiTexCoord0` input, so the composite
  output for 0 is unchanged.
- `DHTerrainTransformer.java`, `DHGenericTransformer.java`: the private copies are removed, and both call the shared
  helper.
- 3.4, `CoreTransformHelper.injectMatrixUniforms`: `replaceExpression("gl_TextureMatrix[2]", "iris_LightmapTextureMatrix")`
  is its own call after the [0]/[1] HashMap and before the catch-all. The catch-all comment and the javadoc are updated.
- Tests: `src/test/java/net/coderbot/iris/pipeline/transform/transformer/CommonTransformerTest.java` (5 tests: the
  bounded range alone, with its declaration kept; the ATTRIBUTES, CELERITAS_TERRAIN and COMPOSITE vertex shaders; the
  COMPOSITE fragment shader left alone) and `CoreTransformHelperTest.java` (2 tests: [0]/[1]/[2]/[3]/[index], and [2]
  alone with no catch-all).
- Mini-corpus (`src/test/resources/transform-corpus/`, engine=douira, out.douira.* recorded BEFORE the change):
  `attributes-multitexcoord-4-7`, `celeritas-terrain-multitexcoord-4-7`, `composite-multitexcoord-1-7` (3.1),
  `attributes-texturematrix-2`, `composite-texturematrix-2` (3.4). There are six `accepted.txt` entries with reasons.

## Deviations from the brief

- Helper written as a ShaderAst verb loop (the lifted DH copy), not as idiom code. The orchestrator preferred this, and
  the reason is in a `// Demonica:` comment.
- The Celeritas call runs after the 0-2 replacements, where upstream runs it after patchMultiTexCoord3. The composite call
  runs before the gl_MultiTexCoord0 rename, where upstream runs it after replacing 0. The names do not overlap, so the
  output is the same.
- 3.4: two mini-corpus cases instead of the one suggested (`composite-texturematrix-2`). `attributes-texturematrix-2` was
  added because ATTRIBUTES is the path upstream's matcher actually serves.
- 3.4 semantics compared with upstream: upstream uses `glTextureMatrix2` only in VanillaCoreTransformer (core-profile
  packs), mapping [1] and [2] to a constant lightmap matrix. Its compat-profile Vanilla/Sodium transformers leave [2] as
  the built-in, and its CompositeTransformer maps [0]-[7] to mat4(1.0). D maps [2] to `iris_LightmapTextureMatrix` (the
  uniform [1] uses, whose BuiltinReplacementUniforms value is that same constant) in ATTRIBUTES, CELERITAS_TERRAIN and
  COMPOSITE, because injectMatrixUniforms is shared. COMPOSITE already diverged for [0]/[1].
- The catch-all array's slot 2 is still `mat4(1.0)`. It is reachable only with a non-literal index. It was left alone to
  keep the change to what the brief names (see Open questions).
- V-game screenshot sweep not run. The item names V-transform only, and no pack-corpus output changed.

## Open questions

- Should the catch-all `mat4[8](...)` put `iris_LightmapTextureMatrix` in slot 2 too, so that `gl_TextureMatrix[i]` with
  a runtime i == 2 agrees with the literal [2]? No corpus pack uses a non-literal index.
- COMPOSITE texture matrices: upstream makes [0]-[7] `mat4(1.0)` in composite passes. D gives [0] `iris_TextureMatrix`,
  [1] and now [2] `iris_LightmapTextureMatrix`. Should composites follow upstream? That was not checked in game. It is a
  pre-existing divergence, now extended to [2].
