### DH 3.3.0 facts (read from the jar with javap)

- `IDhApiRenderProxy.getDhBlockRatioAtlasTextureGlId()` exists in the 1.12.2 API.
- `DhApiRenderProxy` returns a static field. `GlDhMetaRenderer.runRenderPassSetup` sets that field only when
  `Config.Client.Advanced.Graphics.Texture.enableTexturedLods` is on (default `true`, as in
  `run/client/config/DistantHorizons.toml:627`). It sets it right after `GlBlockTextureAtlas.bind()`, which binds the
  atlas to `GL_TEXTURE1` with raw `GL33` calls.
- `ColumnRenderSource` allocates no texture palette when `texturedLodsEnabledAtDetailLevel` is false (option off, or
  detail level above `maxTexturedLodDetailLevel`, default 2). `getTextureSetId` then returns 0.

## Deviations from the brief

- **No `accepted.txt` entries for `dh-generic` or `dh-generic-legacy`**, and no change to the -dh corpus's
  DH_GENERIC fragment. The brief expected both. Iris's `removeUnusedFunctions` (in D's
  `CompatibilityTransformer.transformEach` and upstream's `CompatibilityTransformer:176-188`) removes stand-ins that
  no one calls, and those programs call none. An entry would fail as STALE. The new `dh-generic-textured` case
  exercises the stand-ins instead.
- **Three new mini-corpus cases.** Without them, no case calls the helpers, so the helper text and the geometry path
  would never be compiled or replayed.
- **`StandardMacros.java` changed**, though the item's Files do not name it. It now defines
  `DISTANT_HORIZONS_TEXTURES` as upstream does. Without the macro, BSL never calls the helpers.
- **Fragment blocks are idiom code at the end of each transformer.** Upstream puts them in the middle. PORTING_GUIDE
  rule 3 requires idiom code to come after the verbs.
- **`glUniform1i` instead of upstream's float overload.** Also, nothing is printed when DH has no atlas; upstream
  prints "WHY".
- **V-dh went beyond the brief.** It also ran BSL (the only one of the three packs that calls the helpers) and a
  probe pack. Complementary r5.9.3 calls none of the helpers, so on its own it only shows that the outputs compile
  and that no LOD is black.
- **`core` flag kept at `true`.** D's flag means "core-profile output" (gl_FragData flattening plus the GLSM
  alpha discard); all six D callers pass `true`, and it came with the S5 orchestrator (`8b7b3489`). Upstream's flag
  only turns off its alpha test, which `DHParameters`' `AlphaTest.ALWAYS` turns off for DH anyway. Keeping `true` is
  deliberate.

## Open questions

1. **Raw GL binds from DH vs GLSM's cache.** DH binds its atlas to unit 1 with raw `GL33` calls
   (`GlBlockTextureAtlas.bind`, every DH render-pass setup while textured LODs are on). GLSM caches 2D texture
   bindings (`GLStateManager.glBindTexture`). If DH's raw bind bypasses GLSM, then GLSM may skip the
   `IrisLodRenderProgram.fillUniformData` lightmap bind to unit 1 as redundant, and the DH programs would read DH's
   atlas as `lightmap`. This predates 3.3; I did not check it.
   - Probe and screenshots showed nothing wrong, but none was designed to test the lightmap.
   - A probe that writes `texture(lightmap, ...)` in `dh_terrain` would settle it.
2. **Unit 0 holds DH's atlas after DH draws.** Upstream does the same. GLSM tracks the bind, so later binds go
   through; non-LOD pixels matched between the on and off probe runs.
   - A pack that reads `gtexture`/`texture` in a DH program now reads DH's atlas, as in upstream.
3. **Item 3.3's "assets/lod/shaders/" path is wrong for DH 3.3.0.** The shaders are at
   `assets/distanthorizons/shaders/terrain/gl/`.
